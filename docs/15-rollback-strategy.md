# Step 15: 롤백 절차

> **이 단계의 목표:** 프로덕션 배포 후 문제가 발생했을 때, 이전 정상 버전으로 신속하게 롤백하는 방법을 정리한다.

---

## 15-1. 롤백이 필요한 상황

| 상황 | 심각도 | 예시 |
|------|:------:|------|
| 사이트 완전 다운 | 🔴 긴급 | 빌드 에러가 프로덕션에 배포됨, 500 에러 |
| 주요 기능 장애 | 🟠 높음 | 문의 폼 제출 불가, 솔루션 페이지 빈 화면 |
| UI 깨짐 | 🟡 중간 | 레이아웃 틀어짐, 모바일 메뉴 동작 안 함 |
| 콘텐츠 오류 | 🟢 낮음 | 오타, 잘못된 이미지 |

---

## 15-2. 롤백 방법 비교

| 방법 | 속도 | 난이도 | 적합한 상황 |
|------|:----:|:-----:|-----------|
| **Vercel Instant Rollback** | ⚡ 즉시 | ⭐ | 모든 긴급 상황 (가장 권장) |
| **Git Revert + 재배포** | ~5분 | ⭐⭐ | 특정 커밋을 영구적으로 되돌릴 때 |
| **이전 브랜치 재배포** | ~5분 | ⭐⭐ | 여러 커밋을 한 번에 되돌릴 때 |

---

## 15-3. 방법 1: Vercel Instant Rollback (권장)

가장 빠르고 안전한 방법. Vercel 대시보드에서 클릭 한 번으로 이전 배포로 되돌린다.

### 대시보드에서 롤백

```
① Vercel 대시보드 접속 → 프로젝트 선택

② "Deployments" 탭 클릭
   → 배포 이력이 시간순으로 표시됨

③ 되돌릴 정상 배포를 찾기
   → 각 배포 옆에 상태(✅ Ready)와 커밋 메시지가 표시됨
   → 문제 발생 전 마지막 정상 배포를 확인

④ 해당 배포의 "..." 메뉴 클릭 → "Promote to Production" 선택

⑤ 확인 다이얼로그에서 "Promote" 클릭

⑥ 즉시 프로덕션 도메인이 해당 배포로 전환됨
   → 새 빌드 없이 기존 빌드 결과물을 그대로 서빙
   → 전환 시간: 수 초 이내
```

### CLI에서 롤백

```bash
# 배포 목록 확인
vercel ls

# 출력 예시:
#   Age   Status   Duration   URL
#   2m    Ready    45s        company-homepage-abc123.vercel.app  ← 문제 배포
#   1h    Ready    42s        company-homepage-def456.vercel.app  ← 정상 배포
#   3h    Ready    40s        company-homepage-ghi789.vercel.app

# 정상 배포를 프로덕션으로 승격
vercel promote company-homepage-def456.vercel.app
```

### Instant Rollback의 장점

```
✅ 빌드 불필요 — 기존 빌드 결과물을 그대로 사용하므로 즉시 전환
✅ 코드 변경 없음 — Git 히스토리에 영향 없음
✅ 되돌리기 가능 — 롤백 후에도 최신 배포로 다시 전환 가능
✅ 무중단 — 전환 중 다운타임 없음
```

## 15-4. 방법 2: Git Revert + 재배포

특정 커밋의 변경사항을 영구적으로 되돌리고, 새로운 커밋으로 기록할 때 사용한다.

### 절차

```bash
# ① 문제를 일으킨 커밋 확인
git log --oneline -10
# 출력 예시:
#   a1b2c3d  feat: 문의 폼 리뉴얼     ← 이 커밋이 문제
#   e4f5g6h  fix: 메인 페이지 오타
#   i7j8k9l  feat: 채용 공고 추가

# ② 해당 커밋을 revert (변경사항의 반대 커밋 생성)
git revert a1b2c3d

# ③ revert 커밋 메시지 확인/수정
# 기본: "Revert "feat: 문의 폼 리뉴얼""
# → 필요 시 원인 설명 추가

# ④ main 브랜치에 push → 자동 재배포
git push origin main

# ⑤ GitHub Actions CI 통과 → Vercel 자동 배포
# → 약 3~5분 소요
```

### 주의사항

```
⚠️ git revert은 커밋을 삭제하지 않고, 반대 변경을 새 커밋으로 추가한다.
   → Git 히스토리가 보존되므로 안전하다.

⚠️ 여러 커밋을 revert할 때는 최신 것부터 역순으로:
   git revert a1b2c3d    # 가장 최신 문제 커밋
   git revert e4f5g6h    # 그 이전 문제 커밋

❌ git reset --hard는 사용하지 않는다.
   → 공유 브랜치에서 히스토리를 변경하면 팀원과 충돌 발생
```

## 15-5. 방법 3: 이전 브랜치 재배포

여러 커밋에 걸친 대규모 변경을 되돌릴 때 유용하다.

### 절차

```bash
# ① 정상 동작하던 시점의 커밋 해시 확인
git log --oneline -20
# i7j8k9l  feat: 채용 공고 추가  ← 이 시점이 마지막 정상

# ② 해당 시점에서 롤백 브랜치 생성
git checkout -b hotfix/rollback-to-stable i7j8k9l

# ③ 롤백 브랜치를 원격에 push
git push -u origin hotfix/rollback-to-stable

# ④ GitHub에서 main으로 PR 생성
#    제목: "hotfix: 프로덕션 롤백 (문의 폼 리뉴얼 이전으로)"

# ⑤ PR 머지 → 자동 배포
```

## 15-6. 롤백 판단 기준 (플로차트)

```
프로덕션에서 문제 발견
  │
  ├─ 사이트 다운 또는 주요 기능 장애?
  │   ├─ Yes → Vercel Instant Rollback (즉시)
  │   │         → 이후 원인 분석 및 수정
  │   │
  │   └─ No ─→ UI 깨짐 또는 콘텐츠 오류?
  │              ├─ 단일 커밋이 원인?
  │              │   ├─ Yes → git revert + 재배포 (5분)
  │              │   └─ No  → 롤백 브랜치 + PR (10분)
  │              │
  │              └─ 경미하여 다음 배포에서 수정 가능?
  │                  → 핫픽스 PR 생성 → 빠르게 수정 후 재배포
```

## 15-7. 롤백 후 조치

### 즉시 조치

```
□ 프로덕션 사이트 접속하여 정상 복구 확인
□ 전체 페이지 (/, /about, /solutions, /careers, /contact) 점검
□ 문의 폼 테스트 제출
□ 팀에 롤백 완료 알림 (Slack/이메일)
```

### 원인 분석

```
□ 문제를 일으킨 커밋/PR 식별
□ CI에서 왜 잡지 못했는지 분석
  → 테스트 케이스 누락?
  → 환경변수 차이?
  → 빌드는 성공했지만 런타임 에러?
□ 재발 방지 조치
  → 해당 시나리오의 E2E 테스트 추가
  → 코드 리뷰 체크리스트 보강
```

### 수정 후 재배포

```
□ Feature 브랜치에서 원인 수정
□ 로컬에서 충분히 테스트
□ PR 생성 → CI 통과 확인
□ 프리뷰 URL에서 수정 사항 검증
□ PR 머지 → 프로덕션 재배포
□ 정상 동작 최종 확인
```
